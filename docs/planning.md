# Planning and execution

`plan --env <alias> --out <path>` reads desired IR, fresh normalized Microsoft metadata and the last verified ownership baseline. It performs no remote mutations. `--scope dataverse` explicitly defers app/security intent. All-scope app plans require `--model-driven-experiment` and recorded Experiment 1 evidence for the same project, target and schema. Default additionally requires `--default-experiment` and the dedicated experiment namespace; once app intent is present, use the model-driven policy.

Plans record project/tenant/environment/organization/URL, source hash, observation fingerprint, ownership revision, core/provider versions, one-hour expiry, deterministic operation IDs and dependencies, before/after properties, support/risk/classification and verification strategy. The content hash detects changes; apply also recompiles the operation graph because a hash alone is not authorization.

Unowned collisions, external drift, replaced remote IDs, missing owned resources, managed/noncustomizable components, incomplete discovery, deletions, type replacements, implicit renames and unsupported updates block the entire plan. Developer/sandbox metadata updates are limited to table display/plural labels and column/solution display labels. Default permits creation only, plus scoped publishing of the experiment tables. Choice values are stable numeric identities; option edits are not implemented.

`apply --plan <path> --env <alias>` rechecks target and privileges, locks local project/target state, rediscovers and rejects stale inputs before the first mutation. Each operation rechecks identity and the observed fingerprint. Each mutation gets a durable intent and outcome record. Only verified properties and solution membership advance ownership. A publication fingerprint prevents an interrupted publish from becoming a false no-op.

Transport retries are limited to bounded GET 429/503 responses. GET timeout is 30 seconds and write timeout is 180 seconds. Creates never retry automatically. Bounded postcondition polling accommodates metadata propagation; an API success without matching metadata fails. Execution stops on failure, retains verified checkpoints, and reports completed operations and remediation. There is no automatic rollback, removal or blind resume.

`recover-operation` (alias `recover-create`) provides read-only recovery of a creation after a timed-out request or an acknowledged operation whose postcondition verification failed. It requires the original intact plan, matching journal and its failure/unknown outcome, exact remote GUID, unchanged desired source, verified original target, full matching metadata and solution membership, no other planner blockers, and, for unknown creates, explicit creation-provenance confirmation. Model-driven acknowledged creates require the exact service receipt GUID. A role-grant recovery additionally requires an already-owned parent role and an acknowledged grant; unknown grant outcomes cannot be recovered. Recovery preserves the original journal, adds linked evidence and changes only local ownership. It is not a general adoption command.

A successful apply ends with a fresh three-way semantic no-op. A separate subsequent CLI plan is the Experiment 1 acceptance check. Local executor tests are explicitly synthetic; live evidence is recorded separately.

The experimental model-driven slice is create-only. PowerCanvas app identities use a publisher prefix plus alphanumeric local name, at most 40 characters total. Derived navigation names fit the same bound. App creation sends the local name with the dedicated publisher binding and solution context. In this tenant the raw app name remains local, contrary to the lifecycle documentation's auto-prefix statement. Normalization retains `serviceUniqueName` and checks the creation publisher. A published app can expose the shared unmanaged Active layer's publisher: only an already verified exact app still in the dedicated solution, with published/unmanaged state and separately verified Active solution/publisher, can use this exception. The actual service publisher and dedicated solution publisher remain separate observed fields. Other app IDs, publishers/layers and prefixes fail. This normalized identity is not a claim that the raw service value contains a prefix.

Sitemap's display name is qualified while its service unique name remains local. Normalization retains both actual values and requires their exact relationship plus app-specific scope. The qualified display name is PowerCanvas's sitemap identity. Collision discovery checks qualified, local and display names before creation. App components are read through the observed app layer ID; app access uses a scoped FetchXML query on readable intersect attributes before publication and the published role association afterward. The two platform-created administrator/customizer associations are verified by standard role-template IDs and retained separately. Any other unexpected association blocks verification.

The provider constructs only standard main forms, public views and entity navigation. App validation and a read-back through published endpoints are required before recording model-driven publication evidence. Supported types in the generic IR do not imply every type has a standard form-control mapping in this bounded provider.
