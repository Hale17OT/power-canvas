# Exact provider certification execution

`solution certification-execute` is a policy boundary around the existing native executor and providers. It is not a second compiler/provider or a generic Default-environment write exception. Ordinary native/unified apply still rejects certification manifests.

The command requires an explicit `--execute-reviewed-fixture` instruction, existing environment binding, expected principal, reviewed V2.1d cycle directory, exact fixture and fresh output directory. This flag is appropriate only with operator authorization for the reviewed fixture. It starts with fresh read-only credential initialization, target/WhoAmI, complete discovery and certification planning. It compares the new semantic plan and historical classifications with the reviewed evidence; timestamps and plan instance IDs may differ. Authentication must be healthy. Recovered GET transients are acceptable only with complete observations.

The only accepted source is the V2.1 reviewed fixture/resolved-project hash. Recompilation, exact 21-root/2-dependency counts, risk, dependency graph, Default/nonDisposable policy, identity, ownership, expiry, collision and publication checks must all pass. Mutations outside that contract fail closed, including historical updates, arbitrary additional resources, publication, destructive operations, Canvas/Flow/business data, configuration resources and human/team assignments.

The source-bound execution manifest records solution/publisher IDs, prefix, target, ownership hashes, resource definitions, operation hashes/IDs/risks, dependencies, forbidden resources, empty publication and plan identity/expiry. A short-lived local execution receipt binds those same facts. It contains no credentials and cannot authorize a changed, expired or replayed plan. The executor revalidates under its existing target writer lock, then checks plan/receipt/source integrity and expected ownership progression before each operation. Its own verified receipt updates advance ownership revisions; unrelated revision changes stop execution.

Existing providers execute the native dependency DAG. Each mutation is journaled, read back, verified for defining properties and solution membership, then recorded in ownership. Certification ownership supplements the existing baseline with source/plan hash, creation operation, solution/publisher identity, readback hash, timestamp and revision. The alternate key's existing postcondition requires Active, using the existing bounded polling. No compensation or transactional rollback is claimed.

Writes have no automatic retry. Uncertain writes stop dependent operations and retain the journal; the command attempts read-only reconciliation and reports surviving resources. An uncertain create is never replayed or automatically adopted. Journals remain with the existing single-writer persistence implementation, which serializes, flushes and closes each append. Saved journal/request/auth bytes are hashed after finalization for the evidence index.

Successful provider application must be followed by independent full discovery and a new zero-operation certification plan. `ValidateApp` success and its issue list are recorded without publication. The command reports provisioning as partial until the existing solution export/index verification and explicitly authorized Checker upload are completed. Only completed evidence dimensions can subsequently support capability evidence; runtime/persona, publication, revocation and human/team assignment remain unproven.

Microsoft references: [ValidateApp](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/reference/validateapp?view=dataverse-latest), [PAC solution export and check](https://learn.microsoft.com/en-us/power-platform/developer/cli/reference/solution). Export/Checker do not replace NO_OP convergence or prove production ALM.

Tests exercise exact authorization and rejection of stale/changed plans, identity/ownership changes, forbidden effects, graph edits, unsafe privileges, manifest/receipt tampering and write retries. The positive simulated executor test covers ownership progression, convergence and partial uncertain outcomes. These are offline tests and do not mutate a tenant.
