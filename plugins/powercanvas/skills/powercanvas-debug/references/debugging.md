# Evidence before recovery

Local `doctor --json` checks prerequisites; `doctor --live` or `--env` reads the target. `canvas authoring doctor` connects to official MCP and writes local evidence; it requires current Studio observation. `canvas authoring recover` also connects and acquires live source, then emits an owned-harness removal plan. It is not offline and does not perform the source write. Consult command options rather than guessing them.

Read `capabilities --authoring-evidence <directory> --json` to assess recorded diagnostic/source artifacts without connecting. Fresh artifacts still do not authorize a write. Old evidence is historical; a task journal cannot make it fresh. The existing repository `docs/canvas/design-v45.md` describes source-bound diagnostic capture. Its task-specific runner is not a generic environment configuration utility.

Collect version/commit, sanitized launch overrides, current URL identity, Studio support IDs, connection epoch, capability ladder, timestamps, HTTP status if exposed, safe response details and request IDs. Use `buildAuthoringSupportBundle` for a curated local package. Missing historical response bodies remain missing. Never attach source formulas, business data, cookies or auth caches.

At an external platform blocker, state what passed, where execution stopped, what could not be verified, and the material condition needed for a new bounded attempt. Do not change acceptance/certification because transport availability changed.

`PF-AUTH-001` routes to authentication recovery, never a repeat of solution apply. Use `auth doctor --environment <binding-alias>` for sanitized PAC inventory, the explicitly named PowerCanvas profile, target/WhoAmI and solution/publisher receipts. PAC's active profile is independent of the PowerCanvas MSAL profile. The rebrand retains the legacy `.powerforge/auth` store only while `.powercanvas/auth` is entirely absent; stores are never merged and there is no per-profile fallback.

Inspect profile/store/runtime mismatches read-only. Creating a profile, selecting another account, or rebinding requires explicit operator authorization. Do not print tokens or inspect PAC caches. `--pac` and `--dotnet-root` can select an existing executable/runtime for the diagnostic subprocess without changing global PAC selection. Report source-only changes separately from remote ownership drift. Once authentication recovery passes, stop at read-only readiness; provider certification requires its own task authorization.

`PF-AUTH-006` during discovery routes to credential acquisition diagnosis. A previously working profile is not evidence that it needs recreation. Read the sanitized auth event's stage, state and safe provider code: exact-account lookup, protected-cache access and silent acquisition are separate failure boundaries. Interaction, consent and missing-account states stop the cycle without silent retries or account fallback. Do not clear caches or change bindings to diagnose these events.

`dataverse transport-doctor` now reports independent authentication and Dataverse read health. It requires three complete fresh credential/target/discovery/plan cycles with compatible scope, ownership and observations. Runtime credential reuse is audience/identity bound; it is not an observation cache. Read `docs/solution-v21d-credentials.md` for lifecycle, audit and retry limits. Even a stable preflight does not certify a provider or authorize apply; a separate authorized certification requires another exact fresh plan.

An HTTP 400 stating that `EntityKeyMetadata` / Entity Key `DisplayName` is missing is a provider payload defect. Inspect the typed key contract and Label serializer; do not route it to authentication, transport recovery or platform normalization. A rejected CREATE with independently confirmed absence needs no ownership recovery. A successful CREATE with a Pending/Failed index is a surviving resource: preserve its journal, reconcile read-only and never retry CREATE or delete it automatically. See `docs/solution-v21j-alternate-key.md`.

## Unpublished model-driven apps

A published AppModule association endpoint returning 404, with the same stable app independently verified through unpublished retrieval, means `APP_NOT_PUBLISHED`. It is not evidence to recreate the app, repair authentication or retry transport. With manual publication, retain access as `DEFERRED_REQUIRES_PUBLICATION`. Review exact app-only publication separately. ValidateApp passes with warnings when ValidationSuccess is true and no Error/unknown severity exists; retain the full warning. Draft provider convergence does not prove publication, app access or persona runtime.
